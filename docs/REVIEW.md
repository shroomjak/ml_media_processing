# Ревизия `hailo.cpp`: обработка с NMS, скомпилированным в HEF

Проверялось по исходникам HailoRT (`hailo/hailort.hpp`, `hailort.h`, `vstream.hpp`,
`network_group.hpp`, ветка `master`, v4/v5) и компиляцией `g++ -std=c++17 -fsyntax-only`
против этих заголовков. Платы и DFC в среде не было, поэтому HEF не запускался:
утверждения ниже следуют из API и документации, а не из прогона на железе.

## Главный вывод

В HailoRT **нет** API, включающего NMS на этапе выполнения. NMS целиком задаётся при
компиляции модели в `.alls` (`nms_postprocess(...)`) и «зашивается» в HEF. В рантайме
можно только подкрутить пороги уже скомпилированного NMS:

```cpp
output_vstream.set_nms_score_threshold(0.3f);
output_vstream.set_nms_iou_threshold(0.5f);
output_vstream.set_nms_max_proposals_per_class(100);
```

Отсюда три следствия — два для исходного кода и одно про сегментацию:

1. Вызова `set_postprocessing_config(...)` не существует — файл не собирался.
2. Команды `nms_processing` в DFC тоже нет; правильное имя — `nms_postprocess`, и она
   применяется к модели **до** компиляции, а не в C++.
3. Для instance segmentation на головах YOLOv8/YOLO11/YOLO26 NMS в HEF собрать нельзя:
   DFC поддерживает сегментационный NMS только для `meta_arch=yolov5_seg`. Значит HEF для
   yolo11s-seg/yolo26s-seg всегда отдаёт сырые конвы, и **NMS обязан работать на хосте** —
   он нужен как обычно, по боксам, просто не внутри HEF.

### NMS в `.alls` и сегментация: что именно поддерживается

NMS — это команда **сборки**, а не рантайма: `nms_postprocess` заменяет пару выходов
«бокс + классы» на один выход NMS, и эта замена зашивается в HEF. Поэтому
`set_postprocessing_config` в HailoRT и не существует — менять там нечего.

Поддерживаемые `meta_arch` для `engine=cpu` (по документации DFC): `yolov5`, `yolov5_seg`,
`yolov8`, `ssd`, `yolox`, `centernet`. То есть NMS для сегментации существует — но только
в варианте **`yolov5_seg`**: в HailoRT для него есть отдельный оператор
(`Yolov5SegPostProcess`), который сам перемножает коэффициенты с прототипами и отдаёт
битовые маски в ROI (`HAILO_FORMAT_ORDER_HAILO_NMS_WITH_BYTE_MASK`, поля
`proto_layer_name`, `mask_threshold`, `max_accumulated_mask_size`). Голова YOLOv5-seg
якорная, с objectness — под неё этот оператор и написан.

Для `yolov8`/`yolo11`/`yolo26`-seg такого варианта нет: голова anchor-free с DFL и
отдельными ветвями коэффициентов масок, и Hailo на прямой вопрос отвечает, что
`yolov8m_seg` NMS не поддерживает, постпроцесс надо делать в приложении. Поэтому в model
zoo `yolov8s_seg.alls` состоит только из `normalization` и `change_output_activation`.

### Что происходит, если всё же собрать seg с `nms_postprocess`

Конфиг вида `{classes: 2, regression_length: 16, bbox_decoders: [3 пары reg/cls]}`
синтаксически корректен — он и рассчитан на голову с DFL. Но `meta_arch=yolov8` ждёт
ровно шесть выходов (3 боковых + 3 классовых), а у seg-модели их десять: ещё три ветви
коэффициентов масок и прототипы. Дальше возможны три исхода, и все они проверяются
одной командой `--inspect`:

| Что показывает `--inspect` | Что произошло | Годится для сегментации |
|---|---|---|
| ошибка компиляции DFC | NMS не принял лишние выходы | нет, но это честный отказ |
| один выход `.../nms_postprocess` | ветви масок отброшены, остались только боксы | нет: масок в HEF больше нет |
| 10 сырых выходов | команда проигнорирована, HEF остался прежним | да, но NMS в HEF нет |
| NMS + сырые ветви масок | смешанный вариант | нет: см. ниже |

Последний случай самый коварный. Выход NMS содержит только
`{y_min, x_min, y_max, x_max, score}` по классам — **индекса якоря в нём нет**. Значит
подавленный бокс не с чем связать: 32 коэффициента маски остаются привязанными к ячейкам
сетки, а не к объектам, и сопоставить их можно только повторным матчингом по IoU — с
промахами на перекрывающихся объектах. Именно из-за этого Hailo для seg и оставляет
сырые выходы.

Итог: подавление дублей по боксам и сборка масок для оставшихся объектов считаются на
CPU — функция `nms()` в каждом `.cpp`, вызывается по результатам `decode()`
**до** `build_masks()`. Если в HEF всё-таки окажется NMS-выход,
оба бэкенда теперь падают с объяснением, а не с невнятной ошибкой числа выходов.

## Дефекты исходного `hailo.cpp`

### Не компилируется

| # | Место | Проблема |
|---|---|---|
| 1 | `config.value().set_postprocessing_config(nms_config_path)` | Метода нет у `ConfigureNetworkParams`/`NetworkGroupsParamsMap`. NMS задаётся в `.alls`. |
| 2 | `postprocess()`: `outputs[0].read()` | У `OutputVStream` есть только `read(MemoryView buffer)`. Перегрузки без аргумента нет. |

### Не работает в рантайме

| # | Место | Проблема | Последствие |
|---|---|---|---|
| 3 | конструктор | Нет `group->activate()` | `write`/`read` возвращают `HAILO_STREAM_NOT_ACTIVATED`; `ActivatedNetworkGroup` не хранится |
| 4 | конструктор | `if (inputs.size() != 1 \|\| outputs.size() != 10)` | HEF с NMS имеет 1 выход — требование несовместимо с заявленной целью |
| 5 | цикл по выходам | `if (outputs.size() < 1 \|\| outputs.size() > 2) throw` | проверяется размер вектора, а не число детекций; при 10 выходах условие всегда истинно → конструктор падает всегда |
| 6 | `postprocess()` | повторное чтение уже прочитанных в `infer()` потоков | второй кадр/дедлок, данные из `buffers` игнорируются |
| 7 | формат выхода | `user_buffer_format.order = NHWC` применён и к NMS-выходу | у NMS свой порядок (`HAILO_FORMAT_ORDER_HAILO_NMS_BY_CLASS`); NHWC ломает разбор |
| 8 | разбор | `det_size = 6`, `data[i*6+6+c]` | чтение за границей записи на последней детекции; коэффициенты масок лежат не там |
| 9 | маски | `make_masks(std::vector<Det>{obj}, proto)` | маска пишется во временный вектор, `obj.mask` остаётся пустой |
| 10 | `ids`, `Key` | ключ `{height, features}` без `width` | у NMS-выходов формы вырождены → коллизии ключей |
| 11 | `main` | `HailoModel model(argv[1])` | параметр `nms_config_path` не передаётся: вся NMS-ветка мертва |

### Неверная модель формата

Документированный формат выхода с CPU-NMS (`HAILO_FORMAT_ORDER_HAILO_NMS_BY_CLASS`):

```
для каждого класса: float32 count, затем count × hailo_bbox_float32_t{y_min, x_min, y_max, x_max, score}
```

Класс определяется позицией блока, отдельного поля класса нет. Разбор «6 float на
детекцию» (`x1, y1, x2, y2, score, cls`) не соответствует ни этому формату, ни
`HAILO_FORMAT_ORDER_HAILO_NMS_BY_SCORE` (`uint16 count` + `hailo_detection_t{y_min, x_min,
y_max, x_max, score, class_id}`). Второй порог — нормализация координат: боксы приходят
в `[0, 1]` либо в пикселях, это надо проверять по данным, а не угадывать.

## Что сделано вместо этого

Удалён бэкенд, который пытался включить NMS из HailoRT (`hailo.cpp`): как показано выше,
такой программы быть не может. Примеры `.alls`/NMS-конфига из репозитория тоже убраны —
чтобы никто не собрал по ним seg-модель с надеждой на встроенный NMS.

NMS на CPU при этом никуда не делся: он обязателен и живёт в функции `nms()` каждого
файла, его ревизия — в `docs/NMS_REVIEW.md`.

Код разделён по архитектуре головы, без общего декодера и без общих заголовков:

- `yolo26s_seg.cpp` — YOLO26s-seg: 4 канала бокса (нет DFL), sigmoid на хосте.
- `yolo11s_seg.cpp` — YOLO11s-seg: 64 канала бокса (DFL, softmax по 16 бинам).
- `alls/yolo26s-seg.alls` — базовый model script для seg, без `nms_postprocess`.

Каждая программа самостоятельна: letterbox, декод, NMS, маски, отрисовка и цикл по
кадрам продублированы в обоих файлах. Дублирование намеренное — правка одного файла
не может сломать второй.

Попутно исправлено относительно исходного кода:

- `annotate()` падал на пустой маске (`cv::Mat::at` по пустой матрице) — теперь детекция
  без масок просто не заливается.
- Маски строятся по указателю на прототипы: копия 160×160×32 (3 МБ) на каждый кадр
  больше не нужна; число коэффициентов проверяется.
- Кодек выбирается по расширению выхода: `.avi` → MJPG, иначе mp4v (раньше mp4v
  писался и в `.avi`).
- Все статусы HailoRT проверяются, включая `activate()`: без активации `write/read`
  возвращают `HAILO_STREAM_NOT_ACTIVATED`.
